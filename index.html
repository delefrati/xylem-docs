Xylem · a case for server-first version control

Git wasn't built for agents

Git assumes every clone is a complete copy of the repository that can work offline. Most clones today come from machines that are always online and live for a few minutes.

That design fit kernel maintainers trading patches in 2005. CI jobs, coding agents and sandboxes still pay its full cost: they download history they never read, rebase on their own, and wait in a queue to land. This page makes the case for moving that work to the server.

The shift

The typical repository client has changed

WhoA developer at their own machineA CI job, coding agent or sandbox
LifetimeMonths or yearsMinutes
NetworkOften offlineAlways online
ReadsThe whole tree and its full historyA few directories and a few history questions
CountOne per personMany per person, and more with every agent

The cost

Agents multiply every clone, rebase and queue wait

Repository costs used to grow with headcount. With agents they grow with the number of runs. An engineer with twenty parallel agents is twenty clients, and each one clones, rebases and waits for its turn to land. Put in your own numbers to see the difference between full checkouts and sparse ones.

The idea

Let the server do the work

If clients are always online, the server can hold the history and do the expensive work. Clients become thin. Four things follow.

log · blame · diff · merge-base

History as an API

The server answers history questions directly. A job that needs an answer never needs a working copy, and bisect or auto-revert can run without a single checkout.

clone --sparse

Sparse by default

Clients fetch only the directories and files they work in. Checkout cost follows the size of the task, not the size of the repository.

rebase + compare-and-swap

Landing without a queue

The server rebases a change onto main and moves main with a compare-and-swap. A commit costs O(size of change), and changes that touch different files land in parallel.

content-addressed, immutable

Cache anything, anywhere

Every object is named by its hash and never changes. A cache on the build node, a regional cache or the server can answer any request without coordinating.

What git already handles

Partial clone, sparse-checkout, Scalar and merge queues already make git cheaper to copy, and they cover a lot of the problem. Two gaps remain. History is still something you download and compute locally, not something you can query. And every change still lines up behind a single queue in front of main. Those are the two places where agents hurt most.

Precedent

The largest engineering teams already got here

Google Piper

A centralized server holds one huge monorepo. Developers work in workspaces backed by it instead of local clones.

Meta Sapling and Mononoke

A scalable source control server paired with a client that fetches files and history lazily.

Anthropic Scion

Described in their engineering post on redesigning source control.

Each built its own system because it hit the limits of git first. Agents bring those limits to much smaller teams.

Adoption

You can start without leaving git

  1. Mirror

    Import the git repository and keep it in sync. Git stays the source of truth, and nobody changes how they work.

  2. Read

    Point agents and CI at the server for sparse checkouts and history queries. This is where most of the byte and time savings show up.

  3. Land

    Let agents land through the server, and export each commit back to git so code review, IDEs and existing tools keep working.

  4. Decide

    Move people over only if and when the numbers justify it.

Measure first

Questions to ask your team this week

  • What share of last week's clones were made by people?
  • How many CI minutes go to clone and fetch?
  • How much data does a typical job fetch, compared with the files it actually opens?
  • How long does a change wait to land, at the median and at p90?
  • How often does an agent's change fail to land because of a rebase against files it never touched?

If the answers are "very few", "a lot" and "too long", git's design is costing you more than you think.
