Xylem · use cases

Where Xylem fits

Seven ways to put a server-first version control system to work, from a read-only mirror you can set up in an afternoon to a fleet of agents landing changes at once.

Each use case says what it solves, shows the commands and marks what works today. Most start with a mirror: Xylem imports a git repository and keeps up with it, while git stays the source of truth and nobody changes how they work. For why the design looks like this, see Git wasn't built for agents.

01Works todayExample: llvm/llvm-project

Fast reads of a large monorepo

The problem. LLVM keeps clang, lld, lldb, MLIR, flang, libc++ and more in one repository with a long history. A clang contributor rarely touches flang, but a git clone brings everything. Shallow clones skip history and sparse-checkout skips writing files, but neither skips both.

With Xylem. Mirror the repository once, then clone only the directories you build. The workspace holds the current files of those directories and no history. History questions go to the server.

  • Checkout cost follows the directories you chose, not the repo.
  • xy status only scans those directories.
  • Widen later with xy sparse add, which fetches just that directory.
# once, on the server host
git clone --mirror https://github.com/llvm/llvm-project.git /srv/llvm.git
xylemd import --git /srv/llvm.git --branch main --repo llvm
xylemd server &
# keep the mirror current (plus git fetch from cron)
xylemd import --git /srv/llvm.git --branch main --repo llvm --follow 30s

# a clang developer
xy clone xylem:7400 ~/llvm --repo llvm --sparse llvm,clang,cmake,third-party
cd ~/llvm
xy status
xy sparse add clang-tools-extra

LLVM's main has no merge commits, so its first-parent history in Xylem matches git log exactly. The first import of a history this size takes a while; after that, --follow only processes new commits.

02Works todayExample: any CI pipeline

History as an API

The problem. Many CI steps clone a repository just to read one file, list a directory or ask which paths a commit changed. The clone is most of the job's runtime.

With Xylem. Every history question is a gRPC call: resolve a revision, read a file, list a directory, log, diff, blame, merge-base and ancestry. The xy commands work without a workspace when you pass --server and --repo.

  • Test selection from changed paths without a checkout.
  • Bisect and auto-revert tooling built on Log, IsAncestor and MergeBase.
  • Imported commits stay addressable by their git sha (git:<sha>).
X="--server xylem:7400 --repo llvm"
xy cat llvm/CMakeLists.txt -r main $X
xy ls clang/test/Sema -r main $X
xy log clang/lib/Sema -n 20 --oneline $X
xy show git:3f2c9e1 $X        # changeset + diff, by git sha

# or call the API directly
grpcurl -plaintext -d '{"revision":"main~2"}' \
  xylem:7400 xylem.v1.RepoService/ResolveRevision

Every RPC has a working grpcurl example in docs/api-examples.md.

03Works todayExample: 20 coding agents on one repo

Many agents landing at once

The problem. With git, each agent rebases locally, pushes, finds main has moved, and tries again. Twenty agents make that loop the bottleneck, and a merge queue serializes them all.

With Xylem. xy commit creates a draft on the server; there is nothing to push. xy land asks the server to rebase the draft onto the latest main and move main with a compare-and-swap. There's no global lock.

  • Changes to different files land in parallel.
  • Changes to different parts of the same file merge line by line on the server.
  • Only overlapping edits come back, with exit code 3 and the workspace untouched.
# each agent, in its own small sparse workspace
xy clone xylem:7400 /work/agent-07 --repo app --sparse services/billing
cd /work/agent-07
# … the agent edits files …
xy commit -A -m "billing: retry webhook on 5xx"
xy land
case $? in
  0) echo landed ;;
  3) xy sync ;;   # real conflict: rebase onto main, resolve, retry
esac

Tested with 20 concurrent workspaces under the race detector: every non-conflicting change lands and main stays a valid first-parent chain. Binary files, symlinks and files over 8 MiB conflict as whole files.

04Built, in reviewExample: a CI fleet with short-lived nodes

Shared caches for build farms

The problem. Hundreds of jobs fetch the same files from the same server. Git packfiles depend on what each client already has, so they are hard to cache between clients.

With Xylem. Every object is named by its hash and never changes, so any tier can serve any object without coordination. Run a cache near the fleet and a daemon on each node. Clients talk to the daemon over a Unix socket and can skip their own cache.

  • The server only sees cache misses.
  • Every tier verifies the hashes it receives.
  • If the cache dies, clients get a clean Unavailable error, and the server stays under its in-flight limit.
# regional cache, next to the fleet
xylemd cache --upstream xylem:7400 \
  --disk-dir /var/cache/xylem --disk-bytes 200000000000

# on each build node
xylemd daemon --upstream cache-host:7400 --server xylem:7400

# jobs on that node
xy clone unix://$XDG_RUNTIME_DIR/xylem/daemon.sock /build/src \
  --repo app --sparse services/api --no-cache

Benchmark: 100 concurrent sparse clones through daemon → cache → server, after a 10-clone warm-up, needed 23 server reads for 4,730 object requests (0.49%). The daemon's hit rate was 98.2%.

05Works todayExample: huggingface/transformers

One repo, many independent directories

The problem. Some repositories are a collection of mostly separate units: hundreds of model implementations, plugins, packages or providers. A contributor works on one unit and its tests, yet clones all of them.

With Xylem. A sparse profile of the unit, its tests and the shared utilities is enough. Blame and log on the shared core files, which have long histories, come from the server.

  • Smaller checkouts for contributors and per-unit CI jobs.
  • Each unit's CI fetches only that unit.
  • A medium-sized repo like this is a good first real-world trial.
git clone --mirror https://github.com/huggingface/transformers.git /srv/tf.git
xylemd import --git /srv/tf.git --branch main --repo transformers
xylemd verify-import --git /srv/tf.git --repo transformers --sample 200 --seed 1

xy clone xylem:7400 ~/tf --repo transformers --sparse \
  src/transformers/models/llama,src/transformers/utils,tests/models/llama
xy blame src/transformers/modeling_utils.py

This is about the project's code. Model weights and datasets belong on a hub built for large files; see where Xylem doesn't fit.

06Works todayExample: an ownership dashboard

Code archaeology at scale

The problem. Ownership maps, churn reports and audit tools run git blame and git log across thousands of files. Each call walks history on the local machine, and every run starts over.

With Xylem. Blame and path history are stored on the server, computed incrementally from each changeset's parents. The first request for a file computes and stores its blame; later requests and later revisions reuse it.

  • A dashboard can blame every file under a directory without a checkout.
  • Results are consistent for every client.
  • History follows the first parent, like git log --first-parent.
X="--server xylem:7400 --repo app"
xy ls services/billing -R --json $X | jq -r '.[].name' |
while read -r f; do
  xy blame "$f" --json $X |
    jq -r '.origins as $o | .lines[] | $o[.origin].author.name_email'
done | sort | uniq -c | sort -rn | head
# top authors of lines currently in services/billing

xy log services/billing -n 200 --oneline $X   # churn

Blame matches git on 98.9% of lines in a real 18,923-commit repository. The rest differ where several equally small diffs exist and git breaks the tie differently. Xylem also doesn't follow renames in blame yet.

07PlannedMirror today, export planned

Moving off git as the writer

The problem. Making Xylem the source of truth is a big step if code review, IDEs and existing CI still speak git.

With Xylem. Migrate in phases, with one writer at a time. The import side works today. The export side, xylemd export-git, writes changes landed in Xylem back to git as ordinary commits. It is designed, with a test plan, but not built yet.

  • Phase 1: git is the writer, Xylem mirrors it (works today).
  • Phase 2: freeze git pushes and run a final import.
  • Phase 3: Xylem is the writer, and git becomes the mirror through export (planned).
# phase 1 (works today)
xylemd import --git /srv/app.git --branch main --repo app --follow 30s

# phase 3 (planned)
xylemd export-git --git /srv/app.git --branch main --repo app --follow 30s
git -C /srv/app.git push origin main      # run by you or cron

The planned export produces the same commit sha for the same change every time, so re-runs after a crash are safe. It refuses to write if someone pushed to git on their own, and re-importing exported commits creates no duplicates. Two-way sync, with both sides writing at once, is out of scope.

Honest limits

Where Xylem doesn't fit

Small repositories

If a full clone takes seconds, git is already fast enough. Xylem pays off when clones, status and history get slow, or when many clients share one repo.

Model weights, datasets and big binaries

Files over 64 MiB are rejected and Git LFS isn't supported. Splitting large files into shared chunks is future work. Use a store built for large files.

Offline and distributed workflows

Xylem assumes clients are online. Projects that live on maintainer trees and patches by email, like the Linux kernel, want what git already does.

Shared deployments, for now

Authentication and rate limits are planned next. Until then, run Xylem on a trusted network only.

Submodules

Submodule entries are skipped on import. A repository that depends on them needs another way to fetch those trees.

Branch-heavy workflows

Xylem has main and release refs. Work in progress lives in drafts, not branches. Long-lived feature branches don't map well.

Where to start

Pick one repository that is slow today, mirror it, and point a single CI job or agent at the server (use cases 1 and 2). Compare clone time and bytes fetched before and after. If the numbers are worth it, add the cache tiers, then let agents land.
